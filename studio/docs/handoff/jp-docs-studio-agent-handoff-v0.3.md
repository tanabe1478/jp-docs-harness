## 0. エージェントへの実行指示

**本書は検討資料ではなく実装依頼である。** 最新の `main` を確認し、既存の設計・テストを壊さず、実際に起動できるMVPを実装する。まず短い作業計画と依存関係を示してから実装し、マイルストーン単位でテストする。

1. 初めに `studio-visual-spec-v0.3.md` と `design/focus-desktop.png`、`design/dialog-desktop.png`、`design/proposal-desktop.png` を見てから、既存リポジトリの `README.md`、`package.json`、`docs/product-plan.md`、`docs/semantic-review.md`、`skills/review-docs/SKILL.md`、`bin/jp-docs-harness.mjs` を読む。ソースと本書が食い違えば **現行コードの実際の契約を確認し、無断で既存仕様を変更しない**。
2. `studio/` に実装を追加する。既存のCLI、pi extension、Claude Code Pluginと既存の評価コーパスはそのまま使える状態を維持する。
3. 完成イメージの静的画面を作るだけで終了しない。**ローカルMarkdownの保存、選択箇所に対するAI対話、意思決定、提案差分の承認、検査実行**をつなげる。
4. AIの呼び出しができない場合は、誤魔化して成功表示しない。APIキーなし状態で編集・保存・閲覧・デモ用のテストは動作し、AI操作は設定案内を表示する。テストでは注入可能なFakeAdapterを使うが、通常UIでFake回答を本物のAIとして見せない。
5. 大きな設計変更が必要になったら、問題と代替案を記録する。未実装の機能を完成済みと報告しない。
6. 最後に起動手順、変更ファイル、動作確認の結果、未対応事項、画面キャプチャ（自動UIテストが取れる場合）を報告する。

## 1. コンセプトと設計上の責任境界

> AIと対話しながら、自分の考えを発見し、深め、文章にしていくための静かな執筆環境。

「AIが正しい文章に修正する」ことを中心に置かない。初めて読む読者として解釈を伝え、書き手が違和感・反論・気づきを得られることを中心にする。

- **書き手の権限**: 書く / AIを呼ぶ / AIへ反論する / 提案を採否する / 考えの変化を記録する。原稿本文の変更は本人の明示的操作のみ。
- **AIの役割**: 読者の解釈、曖昧な前提、別視点を示す。事実・推測・本人の意見を混同しない。AIが「本人はこう考えた」と推定して保存しない。
- **既存Harnessの役割**: 見た目や文章の良否の判定、根拠、文書契約への適合、鮮度管理。`needs_author` をAIが補完しない。
- **低干渉**: 入力中・保存時・画面表示時にAIを自動呼び出ししない。通常時はAIパネルを閉じる。

### 今回のユーザージャーニー（必須）

1. ローカルworkspaceを指定してアプリを起動する。
2. Markdownを開く、または作る。静かな画面で考えを書き、保存・再オープンできる。
3. 任意の文を選択して「どう読める？」か「別の見方は？」を押す。
4. AIが **読み取った主張 / そう解釈した理由や前提 / 問いたいことを原則1件** 返す。AIへの送信範囲が分かる。
5. ユーザーは応答、保留、却下、または自身の言葉で「気づき」を記録できる。
6. 明示的に「修正案を作る」を選ぶとAIが選択箇所だけの置換案を返す。差分を確認し、採用または破棄する。
7. 保存・画面再読み込み後も原稿と対話・本人の決定が保持される。`check-docs` を明示実行できる。

## 2. UI / ビジュアル仕様（OmmWriterに影響を受けた独自デザイン）

### デザイン原則

OmmWriter等の具体的な画像、UI配置、音源、アイコン、アートワーク、商標を複製しない。学ぶのは **余白、静けさ、自然な光、執筆への没入、任意の環境音** という抽象原理だけ。独自の画面レイアウトとアセットで実現する。

- 初期テーマ: 温かいオフホワイト `#EAE7DF`、本文 `#363A38`、補助文字 `#74786F`、控えめなセージ `#DCE2D9`。コントラスト比を測って必要なら調整。実装ではCSS変数へ集約する。
- 背景: 単純な平坦色だけでなく、**CSSの淡いグラデーション/抽象的な光のレイヤー**で空気感を出す。外部サイトから未許諾の風景素材を取得しない。
- 文字: 日本語の長文に適した可読性を優先。ローカルに存在する明朝系を第一候補、ゴシックへフォールバック。外部フォントの読み込みは必須としない。固定幅テキストにしない。
- 編集カラム: 最大幅 680〜740px 程度、行長・行間に配慮。画面の中央寄せ、余白を広く取る。文字サイズ 17〜20px 程度（調整可能）。
- ツールバー: 常時視線を奪わない最小限のヘッダとフッタ。キーボード操作でも全機能にアクセス可能。
- AIパネル: 初期非表示。広い画面では原稿カラムの横にオーバーレイ的に現れ、**本文の改行位置を変えない**。狭い画面では別シートとして現れる。閉じると元のカーソル位置に戻れる。
- 背景音: 初期ミュート、**明示的な操作でオン**。MVPではWeb Audioで生成した穏やかな環境音か、権利・出典が明確な同梱音源1種類。音量とミュートを持つ。未実装の再生ボタンは禁止。
- モーション: 控えめ。`prefers-reduced-motion`、フォーカスリング、キーボード、スクリーンリーダーの基本対応。
- UI文言: 日本語。堅い検査画面より、穏やかな執筆空間を優先。ただし失敗や競合は曖昧にしない。

## 3. スコープ確定

### MVPに含める

- `studio/` のブラウザUI（ローカル起動）、Markdownを1件ずつ開く・作る・保存する
- 日本語の執筆に適したエディタと静かな背景、ミュート可能な環境音
- 任意の選択範囲を起点にしたAIの解釈と別視点、対話継続
- 明示的な保留・却下・再開、本人記述のInsight保存
- 選択箇所の置換提案と差分確認、明示的な採用・却下
- 文書、会話、Insight、提案の再起動後の永続化
- `check-docs` の本物の実行と結果表示（CLIの出力を利用）
- 存在する `*.md.intent.yml` の簡単な参照（読み取り専用）。存在しない場合は「未設定」とする
- 自動テスト（ロジックのユニット + 主要フローのE2E）と開発者向けREADME

### 初期スコープ外

- マルチユーザー、クラウドアカウント、共同編集、同期、投稿・公開、モバイルネイティブアプリ
- 全自動の文書生成/校正、自律的なAI割り込み、全文書を毎回LLM Judgeで検査
- `review-docs` のJudgeそのものをWebから独自再実装すること、契約の自動確定
- 思考グラフ、複雑な枝分かれUI、複数モデルの同時討論、WYSIWYG完全対応
- 音源ライブラリ、背景テーマのマーケットプレイス、アニメーション大量追加

**将来統合:** `plan-docs` の対話UI、`review-docs` のpacket/Judge/record/verify、Findingへの紐付け、複数文章横断の思考履歴。今回、将来統合しやすい境界は作るが実装はしない。

## 4. 技術・リポジトリ構成

現行リポジトリ（2026-10-15確認）はNode.js ESM (`"type":"module"`)、Node >=20.18、`bin/jp-docs-harness.mjs`、`lib/run-harness.mjs` と意味レビュー関連CLIを持つ。現行 `package.json` のversionは 0.23.0。**作業開始時に再確認すること。**

推奨実装:

- UI: TypeScript + React + Vite + CodeMirror 6（Markdownテキストを正本として扱う）
- API: TypeScript + Node.js HTTPサーバー（Fastify等でよい）、JSON Schema/Zod等による入力検証
- テスト: VitestまたはNode Test Runner、Playwrightによる主要フロー
- AI: サーバー側の `AiAdapter` インターフェイスで隔離。まず OpenAI API を1つ実装し、モデル名とAPIキーは環境変数で設定。**ChatGPT有料プランとAPI課金は別**。今後pi/Codex/Claude等の実行器を追加できる構造にする
- Workspace: CLI起動時に絶対パスを指定するローカルディレクトリ。サーバーが許可するファイルスコープはその配下だけ
- 永続化: 原稿はworkspace内の `.md` ファイルを直接編集。思考・対話メタデータはOSのアプリデータディレクトリ（またはXDG互換）にworkspace絶対パスのハッシュをキーとして保存し、既存repoを汚さない。MVPはJSONファイルでよい

推奨構成（厳密なファイル名は任意）:

```text
jp-docs-harness/
  bin/ ...                        # 変更しない
  lib/ ...                        # 既存の検証コア。変更は最小限
  studio/
    package.json                 # 独立した依存管理
    README.md
    src/
      client/
        app/
        editor/
        components/
        styles/
      server/
        routes/
        services/
        providers/
        persistence/
        security/
      shared/
        types.ts
    tests/
      unit/
      e2e/
      fixtures/
```

起動契約（エージェントがREADMEに実行可能なコマンドを明記する）:

```sh
cd studio
npm install
npm run dev -- --workspace /absolute/path/to/writing-workspace
```

Windowsのパスもサポートする。開発サーバーは原則 `127.0.0.1` にのみbindし、起動時にアクセスURLを表示する。root packageのCLI/pack対象に不用意にStudioのWeb依存を混ぜない。テスト時はリポジトリルートの `npm test` も通す。

## 5. データモデルと永続化の契約

本文はMarkdownが唯一の正本。対話データを本文へ勝手に書き込まない。

```ts
// 型の基準。実装で同等の型とruntime validationを用意する。
type Anchor = {
  quote: string;               // 選択原文
  start: number;               // JS文字列のUTF-16オフセット
  end: number;                 // end exclusive
  sourceDocumentHash: string;  // SHA-256(UTF-8の本文)
};

type Thread = {
  id: string;
  documentPath: string;        // workspace基準の相対パス
  anchor: Anchor;
  mode: "interpret" | "counterpoint";
  status: "open" | "held" | "dismissed" | "stale";
  turns: Array<{ id: string; role: "author" | "ai"; text: string; createdAt: string }>;
  createdAt: string;
  updatedAt: string;
};

type Insight = {
  id: string;
  threadId: string;
  text: string;                // 本人が入力して保存した文。AI生成物を自動登録しない
  createdAt: string;
};

type Proposal = {
  id: string;
  threadId: string;
  anchor: Anchor;
  replacementText: string;     // AIが返した選択範囲の置換だけ
  status: "pending" | "accepted" | "rejected" | "stale";
  createdAt: string;
};
```

- 原稿は `contentHash` を付けて取得し、保存時はクライアントから `expectedHash` を送る。異なる場合は HTTP 409。**黙って上書きしない**。
- 同じく提案の適用時は原稿のhashとアンカー原文を原子的に確認する。1文字でも競合すれば適用せず、再選択・再提案を促す。
- CodeMirrorのオフセットとサーバーのJS文字列オフセットをともにUTF-16として扱う。ハッシュはUTF-8で計算し、その違いをテストする（日本語・絵文字）。
- 本文変更で `sourceDocumentHash` が不一致になった対話は表示可能だが `stale` として扱う。**推測で別段落へ自動再紐付けしない**。
- メタデータは原子的に保存（tempファイル + rename等）。JSON Schema/バージョンフィールドで将来の移行に備える。
- READMEで対話履歴の保存先と消去方法を説明。workspaceを移動すると紐付けが変わることはMVPの制限として明記。
- ローカルファイルの外部編集・同時編集で競合が起きることを想定する。自動保存はよいが409を適切に提示する。

## 6. APIの最小契約

HTTPの詳細は実装側で調整してよいが、機能ごとの境界は維持する。入力・出力はruntime validation。APIはlocalhost専用とし、任意ファイルシステムアクセスを提供しない。

| 用途 | 例のエンドポイント | 重要な要件 |
| --- | --- | --- |
| 稼働・設定状態 | `GET /api/config` | AI有効/無効・モデル表示。秘密値は返さない |
| 原稿一覧 | `GET /api/documents` | workspace内のMarkdownだけを表示 |
| 原稿取得 | `GET /api/document?path=...` | 相対パス、本文、hash |
| 原稿作成 | `POST /api/documents` | .mdのみ、既存ファイルは上書き禁止 |
| 原稿保存 | `PUT /api/document` | path, content, expectedHash → 409競合 |
| スレッド一覧 | `GET /api/threads?path=...` | 原稿別に取得 |
| スレッド開始 | `POST /api/threads` | path, anchor, modeを検証 |
| AIへ依頼 | `POST /api/threads/:id/assist` | 明示ボタンからのみ。AI設定なしは適切なエラー |
| 人間の返答 | `POST /api/threads/:id/turns` | role は `author` のみクライアントが追加可能 |
| 判断 | `POST /api/threads/:id/decision` | held/dismissed/reopened |
| 気づき | `POST /api/threads/:id/insights` | 人間が入力・確定したテキストだけ |
| 修正案の生成 | `POST /api/threads/:id/proposals` | 特定anchorの置換だけ |
| 修正案の採否 | `POST /api/proposals/:id/decision` | 採用時は原子性を保証し競合で409 |
| 軽量検査 | `POST /api/check` | 指定されたMarkdownだけに既存`check`を実行 |
| 契約表示 | `GET /api/contract?path=...` | `*.md.intent.yml`を読み取り専用表示 |

`check` は既存の `bin/jp-docs-harness.mjs check --format json <relative.md>` を `shell: false` で子プロセス実行する、または公開済みの `runHarness` を呼ぶ。exit 0と1のJSONは通常の結果、2は異常として扱う。タイムアウト・出力上限を設定する。**アプリ独自の新しい判定器を作らない**。ユーザーが検査実行したことが明確なUIにする。

パス境界は単なる `startsWith()` 判定ではなく、正規化後の `realpath`、セパレーターとsymlinkを踏まえて検証。`../`、絶対パス注入、symlinkでworkspace外を参照できないようにする。workspace root自体も起動時に検証し、ファイルは通常サイズ上限（例2MiB）を設ける。

## 7. AIアダプターの実行仕様

```ts
interface AiAdapter {
  respond(input: {
    action: "interpret" | "counterpoint" | "reply" | "propose";
    selection: string;
    surroundingContext: string;
    turns: Array<{ role: "author" | "ai"; text: string }>;
    authorReply?: string;
  }): Promise<
    | { kind: "reflection"; interpretation: string; reasoning: string; question: string; uncertainty?: string }
    | { kind: "proposal"; replacementText: string; rationale: string }
  >;
}
```

- 初回はOpenAI APIのサーバー側アダプターを一つ実装する。環境変数は `OPENAI_API_KEY` と `JP_DOCS_STUDIO_MODEL`。モデル名は明示必須。APIの技術仕様は実装時に公式SDK/ドキュメントで確認する。
- **必ず文書内容を非信頼入力として扱う。** 原稿にある「命令」に従ってツールを使ったり、秘密を開示したりしない。レスポンスはスキーマで検証し、HTMLとして無加工挿入しない。
- 文書全部を暗黙に送らない。原則、**選択テキスト、前後の限定文脈（例各1段落/総量4000文字以下）、当該スレッド直近8ターン**だけを送る。UIで外部送信の範囲と送信先を説明する。
- 検証可能な外部事実は、資料なしに断定しない。interpretは「私にはこう読める」という読み手としての仮説。counterpointは異なる見方を示し質問を原則1件に絞る。
- AIが意図を代弁したり、文章を無許可で書き換えたりしない。
- `propose` は新しい全文ではなく選択範囲の `replacementText` だけを返す。サイズ・空文字・形式異常を検証し、採用前に必ず差分を示す。
- プロバイダーのエラー、課金制限、タイムアウト、接続失敗はUIに明示する。存在しないAI結果を捏造しない。
- APIキーはローカルサーバーの環境変数からのみ読み込み、ブラウザやログ、保存される会話JSONへコピーしない。
- `AiAdapter` のfake実装は自動テストだけに使う。テストでは通常起動から隔離する。

## 8. インタラクション詳細

### 選択 → 対話

- 本文のテキストを選択すると、控えめなポップオーバーで「どう読める？」「別の見方は？」を選べる。
- AIパネルの表示はユーザー操作に紐づけ、選択をsnapshotとして記録する。本文を変更した後の旧選択に新しい回答を誤帰属しない。
- AIの返答は短いカード。「こう読めた」「そう読んだ理由」「確認したいこと」を分ける。長文の汎用記事にしない。
- 書き手の返答には「それは違う」「今は保留」も明示的に使える。議論が止まっても失敗扱いにしない。
- Insight入力は空文では保存しない。AIのまとめをそのまま「本人の気づき」として自動保存しない。

### 提案 → 変更

- ボタン「修正案を作る」から提案を生成。原文と候補の左右比較かインラインdiffを表示。
- 「採用」「破棄」の両方を明示。採用までMarkdownを変更しない。
- 採用後は元の原稿とその一箇所のdiffを残し、通常保存フローに従って即時永続化する。
- 原稿hash/quoteが変わっていれば「元の文章が変更されています。選択し直してください」。提案は `stale` にし、強制適用ボタンを作らない。

### 執筆と音

- エディタはIMEでの日本語変換中（composition）に保存トリガーやAI起動で操作が途切れないこと。
- 自動保存があるなら入力停止後の短いdebounceと手動保存（Ctrl/Cmd+S）を併用。未保存状態を明示。
- サウンドは初期OFF、オン/オフ、音量保存、タブが閉じたら停止。OSの設定が可能ならモーション軽減を尊重。
- 画面が狭い場合でも本文編集ができ、AIパネルを閉じられる。

## 11. 非機能要件

- **安全**: workspace sandbox、localhost bind、許可Originチェック、CSRF対策（可能な限りsame-origin）、CSP、秘密のマスク、ファイルサイズとAI入力長制限。シェルコマンドにユーザー入力を結合しない。
- **ローカル主体**: アカウント必須にしない。Markdownは外部エディタと互換。API送信は人間が起動するときだけ。
- **耐久性**: 原稿・対話・Insight・提案は正常再起動で消えない。書き込み失敗を握りつぶさない。
- **検証可能性**: 人間の承認なしに本文変更を行わないことをテストで保証する。失敗した操作でもUIが成功を示さない。
- **アクセシビリティ**: 色だけで状態を区別しない。ラベル、フォーカス、キーボードでの可操作性。
- **パフォーマンス**: 通常の数千〜数万文字の原稿で入力のたびにLLMや全文検査を走らせない。検査は手動。

1. 書き手の主体性とデータ損失防止
