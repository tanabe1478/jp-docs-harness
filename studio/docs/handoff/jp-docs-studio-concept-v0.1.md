# jp-docs Studio — 製品コンセプト / 中核UX仕様 v0.1

- 状態: 仮説段階（実装確定仕様ではない）
- 対象: `tanabe1478/jp-docs-harness` から発展する執筆ワークスペース
- 作成日: 2026-10-15

## 1. 製品の定義

**AIと対話しながら、自分の考えを発見し、深め、文章にしていく執筆環境。**

AIは文章を完成させる代行者ではなく、書き手の考えを映し出し、問い直し、異なる視点を示す協働パートナーである。文章の所有権と最終判断は書き手に残す。

### 成功の定義

成功とは「AIがより長く、速く、整った文章を書いた」ことではない。**書き手が、自分の主張・根拠・迷いを執筆前より明確に説明できること**と、読者に伝わる文章が得られることの両方である。

思考の深化はAIが一方的に判定しない。書き手本人の確認と、必要に応じて第三者の読解評価を用いる。AIの提案を採用しなかった場合でも、検討によって理由が明確になれば価値がある。

## 2. 解決する課題

1. 文章が整っていても、書き手の本当の意図が伝わっていないことがある。
2. チャットでは議論が文章のどの箇所に対応するか失われやすい。
3. AIが即座に下書きを作ることで、書き手の発想を早期に固定してしまうことがある。
4. AIによるレビューは「欠落を埋める」方向に偏り、前提や目的そのものを問い直しにくい。
5. 執筆途中の保留、反論、判断理由が完成稿に反映される過程が追いにくい。

初期対象は、日本語で技術解説、設計提案、調査ノート、考察文を書く個人。全ジャンル・共同編集・一般向けSNS出版を初期対象に含めない。

## 3. 設計原則

1. **書き手主導**: AIへの依頼、本文への変更、Document Contractの確定は人間が行う。
2. **未完成を許容**: 箇条書き、疑問、矛盾した仮説も書ける。AIが先回りして完成稿へ整形しない。
3. **読者としてのAI**: AIはまず「こう読めた」「ここは判断できない」を返し、正解を断定しない。
4. **反論可能性**: AIへの「違う」「保留」「今回は不要」を正当な操作として扱う。
5. **低干渉**: 書いている最中に自動で質問を表示しない。ユーザーが明示的に呼び出す。
6. **提案と適用を分離**: AIの編集案は差分として保持し、書き手の承認後のみ本文へ反映する。
7. **検証と対話を分離**: 既存ハーネスの機械的な判定と、思考を促す質問・仮説を同一の真偽判定にしない。
8. **ローカルな所有**: 本文はMarkdownを正本とし、外部エディタやGitと併用できるようにする。

## 4. 中核ユーザーストーリー

> 書き手として、いま書いている段落をAIに「初めて読む読者」として読んでもらい、自分の意図と受け取られ方の差に気づきたい。その差について議論した後で、文章を直すか、主張を維持するか、自分で判断したい。

### 最小の体験フロー

1. **記す**: Markdownに考え・仮説・文章を書く（下書きでよい）。
2. **選ぶ**: 気になる一文・段落を選択する。
3. **尋ねる**: 「どう読める？」「反対の見方は？」を明示的に実行する。
4. **受け取る**: AIは（a）読み取った主張、（b）その読みの前提、（c）気になる一点と問い、を簡潔に返す。根拠を示せない内容は推測と表示する。
5. **応答する**: 書き手は返答・反論・保留・却下できる。
6. **判断する**: 書き手が「考えの変化を記録」「変更案を見る」「そのままにする」から選ぶ。強制しない。
7. **反映する**: 文章変更案は差分を見て承認する。変更後は関連する検査結果の鮮度を再評価する。

### 想定例

- 原文: 「AIコーディング時代にはユニットテストの重要性が下がる。」
- AIの読解: 「ユニットテストそのものの価値が下がった、と読めます。」
- AIの問い: 「テストそのものと、テストの組み合わせ・選択基準の変化は区別していますか？」
- 書き手の判断: 「減らしたいのではなく、E2Eと使い分けたい。」
- 記録: 「重要性の低下ではなく、役割の変化が論点だった。」
- 反映: 書き手が文章を改稿。AIが生成した案を採用しても、採用しなくてもよい。

## 5. 最初の画面

```
┌──────────────────────────────────────────────────────────────────┐
│ jp-docs Studio     設計について.md       契約: 確認済み    [検証] │
├─────────────────────────────────────┬────────────────────────────┤
│ Markdown editor                     │ この箇所について            │
│                                     │                            │
│ いま考えていること…                  │ [どう読める？] [反論を探す]  │
│                                     │                            │
│ [選択された段落] ────────────────    │ AI: 私にはこう読めました…  │
│                                     │ AI: 確認したい点は…         │
│ 続きの文章…                          │                            │
│                                     │ [返答] [保留] [却下]        │
│                                     │                            │
│                                     │ [気づきを記録]             │
│                                     │ [修正案を表示]             │
└─────────────────────────────────────┴────────────────────────────┘
```

編集エリアが主役。チャットは文書に付随する。左サイドバー、複雑なタイムライン、思考グラフはMVPでは作らない。AIパネルは閉じて集中できる。

## 6. UIの必須操作

| 操作 | ふるまい |
| --- | --- |
| 段落選択 | 参照箇所を固定し、AIへの入力候補を示す |
| 「どう読める？」 | 読者としての解釈と、曖昧な点を一つ返す |
| 「反論を探す」 | 別の見方・前提への疑問を、事実と推測を分けて提示する |
| 返答 | 選択箇所に紐づく対話を継続する |
| 保留 / 却下 | 問題があると決めつけず、判断として保存できる |
| 気づきを記録 | **本人が確認または記述した**思考メモを残す。AIの推測は本人の意見として登録しない |
| 修正案を表示 | 提案差分を出す。本文はまだ変更しない |
| 採用 | 差分を適用し、元文書の変更履歴を残す |
| 検証 | 既存の`check-docs` / `review-docs`につなぐ（統合時） |

## 7. 状態とデータの最小モデル

### 区別すべきもの

- **Document**: Markdown本文。ファイルが正本。
- **Document Contract**: 読者、読後の変化、必要内容など。既存の`*.md.intent.yml`を使用。
- **Discussion Thread**: 本文の一部に結び付いたAIとの対話。正誤の最終判定ではない。
- **Insight**: 書き手が自ら記録または確認した気づき・意図・保留事項。
- **Proposal**: 本文への変更候補。承認前は本文に反映しない。
- **Review Result**: 既存ハーネスによる検証結果。スナップショットとして扱う。

### MVPで保持するフィールド例

```json
{
  "threadId": "thread-001",
  "documentPath": "docs/article.md",
  "anchor": {
    "quote": "AIコーディング時代にはユニットテストの重要性が下がる。",
    "startOffset": 120,
    "endOffset": 152,
    "documentHash": "sha256:..."
  },
  "topic": "reader-interpretation",
  "status": "open",
  "messages": [],
  "authorDecision": "pending",
  "insightIds": [],
  "proposalIds": []
}
```

アンカーは編集でずれる。MVPでは原文引用と文書ハッシュを保存し、位置を信頼できなくなった場合は**要再関連付け**と表示する。似た文章へ無断で接続し直さない。オフセットの単位（UTF-16等）は実装時に統一する。

対話の記録とレビュー結果のキャッシュは別々に保持する。文書のハッシュが変わると既存レビューは古くなるが、議論の履歴は消さない。

## 8. 既存ハーネスとの境界

### 維持するもの

- `plan-docs` と Document Contract の生成・本人確認
- `check-docs` の決定論的検査
- `review-docs` の根拠、完全性、冗長性などの意味レビュー
- `needs_author` / `uncertain` の責任境界
- Review packet、ハッシュ、記録、鮮度検証、評価コーパス
- CLI、pi、Claude Code からの既存利用

### 新しく作るもの

- Web執筆画面（Markdown編集、選択位置に紐付く対話）
- AIとの対話を扱うアプリケーション層
- 気づき・判断・提案差分の保存
- 検証結果をインライン表示する薄いアダプター

**設計方針:** ハーネスの検査コアはUIに依存させない。Studioが既存CLIやライブラリを利用する方向に依存関係を一方向化する。

## 9. MVP範囲

### 必須

1. ローカルのMarkdownファイルを一件開き、編集・保存できる。
2. 選択箇所についてユーザーがAIに「どう読める？」「反論を探す」を依頼できる。
3. 回答は本文と混同しないパネルに表示し、その箇所に紐付く。
4. 対話への返答・保留・却下ができる。
5. 気づきを本人が記録できる。
6. AIの修正案は差分確認後にのみ適用する。
7. 編集により位置が古くなった対話を識別できる。
8. 本文と対話記録を閉じて再度開いても維持できる。

### 初期スコープ外

- リアルタイム共同編集、アカウント同期、SNS・ブログへの公開
- AIによる無許可の自動修正、常時監視、常時割り込み
- 「思考力スコア」などの単一指標
- 思考グラフの自動生成、複雑なワークフローエンジン
- 多数のAI役割の並列実行と自動討論
- 全文書形式への対応、WYSIWYGとの完全な相互変換

### 初期技術方針（決定前の仮説）

- ブラウザUI + ローカルNode.jsサーバーで開始。
- Markdownテキストを正本とし、補助的状態を別ファイルに保存する。
- AIの呼び出しはアダプターとして分離。特定プロバイダーに固定しない。
- エディタライブラリ等の具体的な技術選定は中核UXの検証後に確定する。

## 10. 評価実験

**検証したい仮説:** 文書の選択箇所に紐付く読者視点の対話は、汎用チャットや単純な文章書き換えより、書き手が自分の意図を明確にする助けになる。

- 被験者: 初期は数人の日本語の技術文書執筆者。一般化できる統計結果を目的としない。
- タスク: 自分の未完成の考察を一定時間執筆し、指定した箇所でAIと議論する。
- 比較: 通常エディタ＋一般的なAIチャットとの比較。順番の影響や題材差を記録する。
- 記録: 執筆前の「何を伝えたいか」、執筆後の説明、採用・却下した提案、本人による有用性・割り込み負担の評価。
- 外部評価: 必要に応じ、完成文から第三者が書き手の主張をどう受け取ったかを確認する。
- 禁止: 対話回数や編集量だけを「思考が深まった証拠」にしない。

### 受け入れ基準

- ユーザーが意図の変化または維持した理由を自分の言葉で記録・確認できる。
- 未承認のAI提案が本文に適用されない。
- 自動的な割り込みがなく、執筆だけに集中できる。
- AIの解釈が外れている場合、「違う」と示して継続できる。
- 本文の編集・保存・再開でデータが失われない。
- 既存ハーネスをStudioなしでも利用できる。

## 11. 主な失敗リスクと対策

| リスク | 対策 |
| --- | --- |
| AIの解釈が書き手の発想を固定する | まず自分で書き、AIは明示的な呼び出しのみ。解釈は仮説と明示 |
| 質問過多で集中が切れる | 1回につき主要な問いを原則1つに絞る。無応答・保留を許容 |
| 文章の「良さ」がAIの好みに均される | 本文の自動書き換えを禁止し、修正案は差分で比較 |
| 執筆履歴がプライバシー上の負担になる | ローカル保存を基本とし、対話の保存・削除を明確化。外部AI送信先を表示 |
| Markdownの編集で議論の参照箇所が崩れる | アンカーを版に紐付け、曖昧な再関連付けは自動確定しない |
| 単なるAIエディタになる | 最初に「読者としての解釈→書き手の応答→気づき」を検証する |
| ハーネスの独立性が失われる | コアのUI依存を避け、アダプター越しに再利用する |

## 12. 推奨実装順

1. **UX試作:** 一画面のMarkdownエディタと選択箇所への読者対話を試作。対話内容が本人の思考に寄与するか観察する。
2. **最小の永続化:** Discussion Thread / Insight / Proposalと本文の関連付け、差分承認を実装。
3. **ハーネス統合:** Contract表示、`check-docs` / `review-docs`、古い結果の表示。
4. **評価:** 通常のAIチャットとの比較、介入頻度・思考の変化・最終文書の伝達度を検証。
5. **拡張検討:** 構想メモの体系化、複数下書き、思考の分岐、検索・資料の整理、デスクトップ化。

## 13. まだ確定しない論点

- AI呼び出しを既存のpi/Codexセッションに委ねるか、専用の実行アダプターを置くか。
- 対話履歴をGit管理するか、個人ローカルなメタデータにとどめるか。
- 文書の選択範囲を粒度細かく追随させるか、段落単位で始めるか。
- `Document Contract`を構想段階のどこで確定させるか。早すぎる固定は探索を妨げる恐れがある。
- UIをハーネスと同一リポジトリに置くか、独立リポジトリに置くか。

これらは先に作り込み過ぎず、最小体験の評価から決める。
