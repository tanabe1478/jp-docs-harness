# GAMUT論文から取り入れる設計

## 対象

- 論文: [Two-Level Meta-Rubrics for Evaluating Open-Ended Generation: GAMUT, a Benchmark for Factual Completeness](https://arxiv.org/pdf/2607.19322)
- 著者: Xilun Chenほか、Meta AI
- コード: [facebookresearch/GAMUT](https://github.com/facebookresearch/GAMUT)

このメモは、GAMUTの手法をjp-docs-harnessへどのように応用するかを整理したものです。論文のベンチマークを再実装する計画ではありません。

## 論文が扱う問題

長文の事実性評価では、文章中の主張が正しいかというprecisionが中心でした。この方法では、書かれた主張の誤りを見つけられても、完全な回答に必要な情報が欠けていないかというfactual completenessを十分に評価できません。

完全性を単純な事実チェックの一覧で表す方法にも限界があります。論文は、特に次の構造を問題として挙げています。

- 選択肢のどれかを一定数含めばよい、開かれた集合
- すべての要素が必要な有限集合
- 各要素だけでなく順序にも意味がある手順
- 複数の対象間にある関係
- 個々の項目だけでは表せない全体的な傾向

GAMUTは、表現力のある構造化ルーブリックと、Judgeが安定して評価しやすい狭いチェックを二段階に分けています。

## 二段階ルーブリック

### 第1段階: 構造化メタルーブリック

完全な回答に必要な内容を、人間が確認しやすい構造で表します。各項目は重要度と型を持ち、根拠となる短い引用へ結び付けられます。

GAMUTの重要度は三段階です。

| 重要度 | 論文における意味 |
| --- | --- |
| `Answer-Critical` | 正しい回答に必須の内容 |
| `Valuable` | 深さ、精度、有用性を大きく改善する内容 |
| `Context` | 理解を助ける背景情報 |

メタルーブリックの型は五つあります。

| 型 | 用途 |
| --- | --- |
| `Simple Knowledge` | 単一の離散的な事実 |
| `Strict List` | 全項目が必要な有限集合 |
| `Flexible List` | 特定項目ではなく一定の網羅率が必要な選択肢集合 |
| `Process` | 順序に意味がある手順 |
| `Relationship` | 対象間の関係、比較、因果 |

リストやプロセスには`meta-insight`を付けられます。これは複数項目を横断する傾向や要約であり、個別項目の存在チェックだけでは評価できない内容です。

### 第2段階: 独立したチェックへのコンパイル

メタルーブリックを、固定規則で自己完結したチェックへ変換します。論文では、この変換を機械的かつ監査可能にすることが設計の要点です。

| メタルーブリック | コンパイル規則 |
| --- | --- |
| `Simple Knowledge` | 一つのチェックへ変換する |
| `Strict List` | 項目ごとに一つのチェックを作る |
| `Flexible List` | 最低限必要な項目数を一つまたは二つの閾値チェックにする |
| `Process` | 各手順の存在チェックと、必須手順の順序チェックを作る |
| `Relationship` | 対象の特定と、関係の各側面を独立したチェックにする |
| `meta-insight` | 割り当てられた重要度で一つのチェックにする |

Flexible Listでは、最低限の網羅率を親と同じ重要度で評価します。追加の網羅性は一段低い重要度へ落とします。短いリストでは項目ごとのチェックを作り、長いリストではチェック数の膨張を避けるために複数の網羅率閾値を使います。論文の実装では、七項目以下を短いリストとして扱っています。

Processでは、必須手順の存在と順序を親と同じ重要度で評価します。任意手順と、任意手順を含む完全な順序は一段低い重要度へ置きます。

生成した各チェックは、他のチェックや外部の暗黙的文脈を参照せず、単独で判定できる必要があります。

## Judgeの判定

GAMUTのJudgeは、各チェックを独立して四状態で評価します。

| 判定 | 意味 |
| --- | --- |
| `meets` | 必要な内容を正しく満たす |
| `partially_meets` | 方向は正しいが、具体性や網羅性が不足する |
| `missing` | 必要な内容がない |
| `contradicts` | 読者を誤らせる実質的な矛盾がある |

欠落と矛盾を分ける点は重要です。慎重に省略した回答と、自信を持って誤った回答を同じ不合格として扱わず、後者を重く扱えます。

論文のGAMUT scoreは、`meets = 1`、`partially_meets = 0.5`、`missing = 0`、`contradicts = -2`として重要度別の値を計算し、Answer-Critical、Valuable、Contextを`0.6`、`0.3`、`0.1`で重み付けします。

jp-docs-harnessの製品判定では、この総合スコアをそのまま採用しません。単一スコアを合格条件にすると、重要な一件の欠落を多数の軽微な項目で相殺できるためです。数値集計は、evalにおけるモデルやプロンプトの比較指標としてのみ検討します。

## 根拠と人間による確認

GAMUTでは、各メタルーブリックを短いWeb引用へ結び付けています。LLMが質問とルーブリックの候補を作りますが、最終データは人間のアノテーターが確認、修正します。ルーブリック作成では、初稿に引きずられない独立検索と、引用元の再確認も行います。

この設計から、jp-docs-harnessでは次の方針を採用します。

1. メタルーブリックの作成者と承認者を記録する
2. 検証可能な事実は、許可された資料中の引用へ結び付ける
3. LLMが生成した契約やルーブリックを未確認のまま厳格モードで使わない
4. 既存ルーブリックの監査と、不足を探す独立した調査を分ける
5. 根拠の追加後にチェック一覧を固定規則で再生成する

## jp-docs-harnessへ採用する部分

### 構造化された要件

`*.intent.yml`の`requirements`を、単純な文字列一覧から型付きメタルーブリックへ発展させます。初期版では簡単な文字列も受け付け、`Simple Knowledge`として扱います。

```yaml
requirements:
  - id: install-flow
    importance: answer-critical
    type: process
    description: Claude Code Pluginの導入手順
    ordered_steps:
      - text: marketplaceを追加する
        mandatory: true
      - text: Pluginをインストールする
        mandatory: true
      - text: Pluginを再読み込みする
        mandatory: true
```

### 決定論的なコンパイラ

LLMに最終チェック一覧を自由生成させず、メタルーブリックから固定規則でコンパイルします。LLMはメタルーブリック案の作成と各チェックの判定を支援できますが、重要度の継承やチェック展開はコードが担当します。

### 狭いJudgeタスク

Judgeには文書全体の品質点を求めません。自己完結したチェックを一件ずつ判定させ、判定、理由、本文の根拠行を返させます。

### 欠落と矛盾の分離

`missing`と`contradicts`を分けます。`contradicts`は、単なる精度不足ではなく、読者を実質的に誤らせる内容に限定します。

### ルーブリックの由来

コンパイル済みチェックから、元のメタルーブリック、文書契約、根拠資料まで追跡できるようにします。

## 本プロジェクト独自の拡張

GAMUTは、根拠に基づく長文回答のfactual completenessを測るベンチマークです。jp-docs-harnessは、目的の異なる文書を執筆中に検証する開発ツールです。そのため、次の概念は本プロジェクト独自の拡張です。

| 拡張 | 理由 |
| --- | --- |
| `needs_author` | 書き手の経験や判断をAIに創作させないため |
| `uncertain` | 根拠不足や曖昧な契約を不合格へ押し込まないため |
| `repairableByAgent` | 自動修正と人間への差し戻しを分けるため |
| `reader_delta` | 読後の理解、判断、行動を文書目的として定義するため |
| 文書プロファイル | チュートリアル、提案書、エッセイなどの差を扱うため |
| 結果の鮮度管理 | 編集中の本文と契約に古い評価を適用しないため |
| Surface gate | 意味検査より安価なtextlintを先に実行するため |

`needs_author`と`uncertain`は、GAMUTの四判定とは別の実行制御です。Judgeによる内容判定と、ハーネスによる責任境界を同じフィールドへ混ぜない設計を検討します。

たとえば、`verdict: missing`かつ`resolution: needs_author`のように表現できます。

## そのまま一般化してはいけない結果

論文では、14モデルの順位が三種類のJudgeでおおむね安定したと報告されています。ただし、これはGAMUTの英語中心のデータ、検証済みルーブリック、所定のJudge promptに対する結果です。

次の事項は、jp-docs-harnessのevalで改めて検証します。

- 日本語文書でもJudge間の一致が維持されるか
- 技術文書以外のプロファイルでも狭いチェックが有効か
- 作成者とJudgeが同じモデルの場合に自己評価の偏りが出るか
- `needs_author`を含む判定で人間との一致率を保てるか
- 行番号を要求した場合に根拠位置が正確か
- Flexible Listの七項目という境界が本プロジェクトにも適切か

論文のスコアや閾値を日本語文書へ直接移植せず、`eval/`の対比例で決めます。

## 実装へ与える要件

GAMUTを参考にする機能は、少なくとも次のテストを通す必要があります。

1. 同じメタルーブリックから常に同じチェック一覧を生成する
2. Strict Listの各必須項目を独立したチェックへ変換する
3. Flexible Listの最低網羅率と追加評価を異なる重要度へ変換する
4. Processの存在と順序を別々に判定する
5. Relationshipを対象特定と関係の側面へ分解する
6. すべてのチェックから元のメタルーブリックへ戻れる
7. `missing`と`contradicts`を区別する回帰例がある
8. LLMが作成した未承認ルーブリックを厳格モードが拒否する

## 本計画における位置付け

GAMUTから採用する中心的な考え方は、次の一点です。

> 完全な文書の構造は表現力のあるメタルーブリックで定義し、実際の判定は固定規則で生成した狭いチェックへ分解する

この方法はCompletenessとGroundingの一部に適用できます。一方、文章の面白さ、段落の寄与、書き手の責任を直接証明するものではありません。Contribution、Genericity、Accountabilityには別の評価設計と独自の回帰コーパスが必要です。
