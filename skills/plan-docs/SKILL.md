## 対象を決める

`$ARGUMENTS`にMarkdownのパスが指定されていれば、それを対象にしてください。本文はまだなくて構いません。

指定がない場合は、依頼内容から一件に絞れるならそのパスを使います。絞れなければ、保存先のパスを利用者へ質問してください。

対象のディレクトリで`git rev-parse --show-toplevel`を実行し、属するGitリポジトリを特定してください。以降の`<REPO_ROOT>`はその絶対パス、`<TARGET>`はリポジトリルートからのMarkdownパスです。Gitリポジトリに属さない場合は、ファイルを置くディレクトリを`<REPO_ROOT>`、ファイル名を`<TARGET>`とします。

`${CLAUDE_PLUGIN_ROOT}`がシェルで未設定の場合は、このスキルのベースディレクトリの二階層上（プラグインルート）の絶対パスへ読み替えてください。

`<REPO_ROOT>/<TARGET>.intent.yml`がすでにある場合は、「書き手に確定してもらう」から始めてください。利用者が見直しを求めた点だけを変更し、契約を作り直してはいけません。

## 文書契約を作る

文書契約は、本文から独立した判定基準です。AIが本文から逆算した契約は本文の要約になり、本文から抜けている内容を見つけられません。読者、読後に得てほしいこと、書き手にしか書けない情報は書き手が決めます。AIは質問して聞き取り、要件を組み立てます。

### プリセットを読む

`${CLAUDE_PLUGIN_ROOT}/presets/`の各ファイルを読んでください。プリセットは文書の種類ごとに、定石の観点（`requirements`）と、読後の変化や書き手にしか書けない情報の候補（`reader_delta_hints`、`author_only_hints`）を持ちます。

### 書き手に聞く

AskUserQuestionで、次の四つを一度に聞いてください。

| header | 質問 | 選択肢 |
| --- | --- | --- |
| 文書の種類 | この文書はどの種類に近いですか | 各プリセットの`title`。どれにも当たらなければ「その他」で答えてもらう |
| 読後 | 読んだ人に、何を分かって、決めて、してほしいですか | 依頼内容とプリセットのヒントから作った候補を2〜4件。`multiSelect: true` |
| 読者 | 主な読者は誰で、何をすでに知っていますか | 依頼内容から作った候補を2〜4件 |
| 書き手だけ | あなたにしか書けない経験や判断理由で、必ず入れたいものはありますか | `author_only_hints`と依頼内容から作った候補と「特にない」。`multiSelect: true` |

候補は依頼内容とプリセットから作る仮説です。本文がある場合も、本文の見出しを並べ直しただけの候補にしないでください。書き手が選ぶか「その他」で答え直すことで、契約の出どころが書き手になります。

### 契約を組み立てる

書き手の答えから、次のように組み立ててください。

- `reader_delta`: 「読後」の答えを、分かること（`know`）、決められること（`decide`）、できること（`do`）に分ける
- `audience`: 「読者」の答え。読者が困っていることを`problem`、すでに知っていることを`knows`にする
- `evidence.author_only`: 「書き手だけ」の答え。「特にない」なら書かない
- `requirements`: 選んだプリセットの観点を、書き手の答えを使ってこの文書向けに具体化する。読後の変化に欠かせないものを`critical`、あると価値が上がるものを`valuable`、背景を`context`にする。本文にあるという理由だけで要件にしてはいけません
- `profile`と`preset`: 選んだプリセットの値。「その他」の場合は`profile`だけを選び、`preset`は書かない
- `non_goals`: プリセットの値と、書き手の答えから読める書かないこと

根拠資料は、実在を確認できるパスか利用者が示したURLだけを`evidence.sources`へ加えてください。書き手の経験や動機を推測して`author_only`へ足してはいけません。

```yaml
version: 1
profile: decision-proposal
preset: decision-proposal

audience:
  knows:
    - 読者がすでに知っていること
  problem:
    - 読者が困っていること

reader_delta:
  know:
    - 読後に分かること
  decide:
    - 読後に決められること
  do: []

requirements:
  critical:
    - 読後の変化に欠かせない内容
  valuable: []
  context: []

evidence:
  author_only:
    - 書き手にしか書けない経験や判断理由
```

契約を`<REPO_ROOT>/<TARGET>.intent.yml`へ書いてください。

## 書き手に確定してもらう

契約の要約を表示します。

```console
cd "<REPO_ROOT>"
node "${CLAUDE_PLUGIN_ROOT}/scripts/claude-review-cli.mjs" contract "<TARGET>"
```

要約を選択肢の`preview`へそのまま入れ、AskUserQuestionで確定を求めてください。質問は「この文書契約で確定しますか。直したい点があれば『その他』に書いてください」とし、headerは「契約の確認」とします。選択肢は次の二つです。

- 確定する: 書き手が契約の内容を確かめた
- 確認せずに進める: 契約は未確認のまま残り、以後の判定には「未確認の契約に基づく」と付く

「確定する」が選ばれた場合だけ、確認を記録してください。

```console
cd "<REPO_ROOT>"
node "${CLAUDE_PLUGIN_ROOT}/scripts/claude-review-cli.mjs" confirm "<TARGET>"
```

「その他」で修正を求められた場合は、その点だけを契約へ反映し、要約を表示し直してもう一度確定を求めてください。

確認の記録は、書き手が「確定する」を選んだときにだけ実行します。AIの判断で実行してはいけません。確認は契約の内容に結び付くため、確定後に契約を書き換えると確認は外れます。

AskUserQuestionを使えない環境（非対話の実行など）では、質問の代わりに依頼内容とプリセットから契約を作り、確認を記録せずに進めてください。最後の報告で、契約が未確認であることと、対話できる環境でplan-docsかreview-docsを実行すれば確定できることを伝えます。

## 執筆へ引き渡す

利用者が執筆も依頼している場合は、確定した契約を執筆の指示書として扱ってください。

- `requirements.critical`をすべて本文に含める
- `evidence.author_only`の内容は、書き手から聞いた内容だけで書く。まだ聞いていなければ、書く前に質問する
- `non_goals`は書かない
- `audience.knows`にあることは説明しない
- `reader_delta`のどれにも寄与しない段落を足さない

書き終えたら、review-docsで本文が契約を満たすかを確かめられることを伝えてください。

最後に、契約のパス、確認状態、選んだプリセット、書き手に聞いた内容を簡潔に報告してください。
